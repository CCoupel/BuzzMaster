## Scénario 6 — ACK timeout : buzzer ancien sans support ACK (rétrocompatibilité)

**Objectif** : Vérifier qu'un buzzer sans firmware ACK ne provoque aucun crash ; timeout silencieux.

> Simulable avec `ack_max_retries=1` et `ack_timeout_ms=500` dans config.json pour accélérer.

| Étape | Action | Résultat Attendu | Résultat Obtenu | OK ? |
|-------|--------|-----------------|----------------|------|
| 1 | Connecter un buzzer avec firmware < 3.8.0 (ou simuler avec wscat ne renvoyant pas ACK) | Buzzer connecté sur `/ws/buzzer` | | |
| 2 | Lancer une question → LED_SET envoyé avec MSG_ID | Badge ⏱ apparaît dans l'interface admin | | |
| 3 | Ne pas envoyer de ACK (ancien firmware) | Le serveur attend `ack_timeout_ms` | | |
| 4 | Attendre `ack_timeout_ms × (ack_max_retries + 1)` ms | Plusieurs LED_SET retentés (visible dans les logs `/admin/logs`) | | |
| 5 | Après max retries | Badge ⏱ **disparaît** (AckPending=false) — **aucun crash serveur** | | |
| 6 | Vérifier les logs serveur | Message WARN "ACK timeout" visible dans les logs | | |
| 7 | Vérifier que le jeu continue normalement | Aucun blocage, la partie continue | | |

**Verdict** : [ ] PASS  [ ] FAIL
