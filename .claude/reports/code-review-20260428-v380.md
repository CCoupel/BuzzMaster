### [MAJEUR-1] Race condition dans `BroadcastToTypes` — double close channel possible

- **Fichier** : `server-go/internal/server/websocket.go` — méthode `BroadcastToTypes`
- **Description** :  
  La méthode `BroadcastToTypes` tient un `RLock` pendant qu'elle itère sur les clients et appelle `close(client.Send)` sur les clients lents (canal plein). Or `sync.RWMutex` autorise plusieurs lecteurs simultanés. Si deux goroutines appellent `BroadcastToTypes` en parallèle (ex : ticker `broadcastTimerUpdate` + un handler WebSocket), les deux peuvent atteindre le `default:` du select pour le même client et toutes deux appeler `close(client.Send)` → **panic "close of closed channel"**.

  De plus, entre le `RUnlock` et le `Lock` pour la suppression de la map, la goroutine `Run()` pourrait (si `Broadcast()` est appelé) obtenir le WLock, voir le client toujours dans la map, et tenter d'envoyer sur un canal fermé → **panic "send on closed channel"**.

  En pratique, le path `Broadcast()` sur `wsHub` n'est plus invoqué (tout remplacé par `BroadcastToTypes`), mais le fallback `a.wsHub.Broadcast(msg)` dans `broadcast()` quand `len(types)==0` subsiste. La double-close sous RLock concurrent reste le risque le plus réel.

- **Suggestion** :  
  Remplacer le pattern `close` + `delete` en deux étapes par un passage sous `WLock` unique. Alternative simple : utiliser un flag `closed` atomique sur `WebSocketClient` avant de close le canal, protégé par le WLock de la map.

  ```go
  // Pattern sûr : toujours sous WLock pour close + delete
  func (h *WebSocketHub) BroadcastToTypes(msg *protocol.Message, types ...ClientType) {
      ...
      h.mu.Lock()  // WLock direct — sérialise les closes
      for client := range h.clients {
          if !typeSet[client.Type] { continue }
          select {
          case client.Send <- data:
          default:
              close(client.Send)
              delete(h.clients, client)
          }
      }
      h.mu.Unlock()
  }
  ```
  Cette approche est cohérente avec le pattern déjà utilisé dans `Run()`.

### [MAJEUR-2] `OnRetry` génère un nouveau MSG_ID — incohérence avec le contrat ACK

- **Fichier** : `server-go/cmd/server/main.go` — `App.init()`, câblage `ackManager.OnRetry`
- **Description** :  
  `OnRetry` appelle `a.resendLEDOnReconnect(mac)`, qui appelle `sendLEDSet()`, qui génère un **nouveau** `msgID` via `generateMsgID()` et crée une nouvelle entrée dans `pendingAcks`. L'entrée originale reste en place et continue de déclencher `OnRetry` à chaque tick jusqu'à expiration (après `AckMaxRetries`).

  Résultat : pour chaque LED_SET non ACKé, 3 appels `OnRetry` × nouvelle entrée = 3 nouvelles entrées enregistrées, chacune déclenchant 3 retries supplémentaires. L'accumulation est bornée (`AckMaxRetries²` max) mais cause :
  - Des rafales de N × N LED_SET redondants vers le buzzer
  - Des logs trompeurs ("retry 1/3", "retry 2/3", "retry 3/3" pour l'entrée originale **et** pour chaque nouvelle entrée)
  - Le firmware v3.8.0 ACKe chaque message avec son propre msgID — les ACKs des retries confirment les nouvelles entrées, jamais l'originale qui expire uniquement par timeout

  Le contrat `contracts/buzzer-ack-protocol.md` stipule : « si timeout et attempts < max_retries → retenter (sendMessage + attempts++) ». Le retry devrait utiliser le **même MSG_ID** pour que le buzzer puisse confirmer le bon slot.

- **Suggestion** :  
  Stocker le payload original dans `AckEntry` (ou dans une map séparée `ledStateAtAck map[string]LEDSetPayload`). Dans `OnRetry`, reconstruire le message avec le msgID original et l'envoyer via `buzzerHub.SendToClient` directement, sans passer par `sendLEDSet()`.

  ```go
  a.ackManager.OnRetry = func(mac, msgID string) {
      // Resend the stored payload with the SAME msgID
      if payload, ok := a.bumperLEDState[mac]; ok {
          msg, _ := protocol.NewMessage(protocol.ActionLEDSet, payload)
          msg.MsgID = msgID  // même msgID — le buzzer confirmera le bon slot
          a.buzzerHub.SendToClient(mac, msg)
      }
  }
  ```

### [MAJEUR-3] N appels `broadcastUpdate()` dans `sendLEDSetAllBuzzers` — régression performance

- **Fichier** : `server-go/cmd/server/main.go` — `sendLEDSet()` + `sendLEDSetAllBuzzers()`
- **Description** :  
  `sendLEDSet()` appelle maintenant `a.broadcastUpdate()` à chaque envoi (pour propager `ACK_PENDING=true`). Or `sendLEDSetAllBuzzers()` appelle `sendLEDSet()` en boucle pour chaque buzzer connecté. Avec N buzzers :
  - N × sérialisation du game state complet
  - N × `BroadcastToTypes(Admin+TV+VPlayer)` — chaque client web reçoit N UPDATE successifs
  - N × `engine.UpdateBumper` avec marshal/unmarshal

  Avant v3.8.0, `broadcastUpdate()` n'était appelé **qu'une seule fois** après `sendLEDSetAllBuzzers()`, dans chaque `broadcastStart/Stop/Pause/Continue/...`.

  Pour 10 buzzers : 10 UPDATE consécutifs par round de jeu. Cela génère du trafic redondant et peut provoquer des microjitters sur les clients TV pendant les transitions de phase.

- **Suggestion** :  
  Déplacer la mise à jour `ACK_PENDING` hors de `sendLEDSet()`, et l'effectuer en batch dans les callers de `sendLEDSetAllBuzzers()` après la boucle :

  ```go
  func (a *App) sendLEDSetAllBuzzers() {
      // ... boucle sendLEDSet sans broadcastUpdate individuel ...
  }
  // Dans broadcastStart(), broadcastStop(), etc. :
  a.sendLEDSetAllBuzzers()
  a.broadcastUpdate()  // 1 seul UPDATE à la fin, pas N
  ```
  Alternative : ajouter un paramètre `suppressBroadcast bool` à `sendLEDSet()`.

### [MINEUR-2] `AckManager.Start()` avec `context.Background()` — goroutine non cancellable

- **Fichier** : `server-go/cmd/server/main.go:542`
- **Description** : `go a.ackManager.Start(context.Background())` démarre une goroutine qui ne peut pas être arrêtée proprement lors d'un graceful shutdown.
- **Suggestion** : Utiliser le contexte applicatif ou créer un contexte annulable dans `App.start()` et passer `a.ctx` (ou un dérivé).

---

### [MINEUR-3] `sendStateToClient` envoie QUESTIONS et CLIENTS à tous les types (TV, VPlayer)

- **Fichier** : `server-go/cmd/server/main.go` — `sendStateToClient()`
- **Description** : (Issue pré-existante, non introduite par v3.8.0) Lors de la connexion initiale (HELLO), `sendStateToClient` envoie QUESTIONS (avec réponses) et CLIENTS à n'importe quel client, quel que soit son type. Un client `/ws/tv` reçoit donc la liste des questions avec leurs réponses.
- **Suggestion** : Vérifier le type du client avant d'envoyer QUESTIONS et CLIENTS. Ces messages devraient être réservés aux clients `admin`.

---

### [MINEUR-4] `broadcast()` conserve un fallback `wsHub.Broadcast()` non typé

- **Fichier** : `server-go/cmd/server/main.go:1667`
- **Description** : La fonction `broadcast()` comporte un chemin `if len(types) == 0 { a.wsHub.Broadcast(msg) }`. En pratique, toutes les call sites passent des types explicites, mais ce fallback reste une porte ouverte à une régression silencieuse (broadcast non filtré à tous les clients).
- **Suggestion** : Supprimer le fallback `wsHub.Broadcast` et remplacer par `a.wsHub.BroadcastToTypes(msg, server.ClientTypeAdmin)` par défaut, ou passer à une signature non variadique.
