## Vérification des Réserves MAJEURES du Reviewer

### MAJEUR-1 — Race condition `BroadcastToTypes` (websocket.go)

**Statut : ✅ CORRIGÉ**

Analyse statique de `server-go/internal/server/websocket.go` lignes 254–270 :

```go
// Use a single WLock so that close(client.Send) and delete(h.clients, client)
// are atomic with respect to concurrent BroadcastToTypes calls.
// A two-phase RLock+WLock upgrade would allow two goroutines to both close the same
// channel between the RUnlock and the WLock, causing a "close of closed channel" panic.
h.mu.Lock()
for client := range h.clients {
    ...
    select {
    case client.Send <- data:
    default:
        close(client.Send)
        delete(h.clients, client)
    }
}
h.mu.Unlock()
```

Le commentaire et l'implémentation confirment que `h.mu.Lock()` (WLock) est utilisé, éliminant la double-close concurrent. La correction recommandée par le reviewer est exactement celle appliquée. `TestBroadcastToTypes_ConcurrentSafety` : PASS.

Note : le test `-race` n'a pas pu être exécuté (CGO requis, gcc absent en WSL). L'analyse statique confirme la correction.

### MAJEUR-2 — `OnRetry` génère un nouveau MSG_ID (main.go)

**Statut : ✅ CORRIGÉ**

Analyse de `server-go/cmd/server/main.go` lignes 234–248 :

```go
a.ackManager.OnRetry = func(mac, msgID string) {
    // Resend the LED payload with the ORIGINAL msgID so the buzzer can confirm the right entry.
    // Never call sendLEDSet() here — that generates a new msgID, leaving the original entry
    // permanently unconfirmable and cascading into AckMaxRetries² slots at most.
    if payload, ok := a.bumperLEDState[mac]; ok {
        msg, err := protocol.NewMessage(protocol.ActionLEDSet, payload)
        ...
        msg.MsgID = msgID // Original msgID, not a new one
        a.buzzerHub.SendToClient(mac, msg)
    }
}
```

Le commentaire est explicite : `sendLEDSet()` n'est pas appelé, `msg.MsgID = msgID` réutilise le msgID original. Comportement conforme au contrat `contracts/buzzer-ack-protocol.md`. `TestAckManager_RetryOnTimeout` : PASS.

### MAJEUR-3 — N appels `broadcastUpdate()` dans `sendLEDSetAllBuzzers` (main.go)

**Statut : ✅ CORRIGÉ**

Analyse de `server-go/cmd/server/main.go` lignes 1979–1983 (sendLEDSet) :

```go
// NOTE: broadcastUpdate() is intentionally NOT called here — callers are responsible for
// a single broadcast after the full loop completes, avoiding N redundant UPDATE messages.
a.ackManager.Register(mac, msgID, protocol.ActionLEDSet)
a.engine.UpdateBumper(mac, map[string]interface{}{"ACK_PENDING": true})
```

Et lignes 2346–2347 (sendLEDSetAllBuzzers) :

```go
// One broadcast for all AckPending state changes set by the loop above.
a.broadcastUpdate()
```

Et lignes 1998–1999 (broadcastLEDSet) :

```go
// One broadcast for all AckPending state changes set by the loop above.
a.broadcastUpdate()
```

`sendLEDSet()` ne déclenche plus `broadcastUpdate()`. Le broadcast unique est fait après la boucle complète. La régression performance est éliminée.

## Race Detector

**Statut : NON EXÉCUTABLE dans cet environnement**

Le flag `-race` de Go requiert CGO activé avec un compilateur C. En WSL (Ubuntu), le binaire `gcc` n'est pas installé (uniquement `gcc-13-base` et `gcc-14-base`, qui sont des méta-paquets sans le compilateur). La commande `go test -race` retourne `go: -race requires cgo; enable cgo by setting CGO_ENABLED=1`.

**Mitigation :** L'analyse statique du code confirme que la race condition MAJEUR-1 est corrigée par le WLock en place. Le test `TestAckManager_ConcurrentAccess` (sans `-race`) passe. La CI GitHub Actions (Linux + gcc disponible) pourra exécuter le race detector sur le push.
