## Résumé

Trois features orthogonales pour v3.8.0 :

1. **#11** — Endpoints WS dédiés par type de client (`/ws/admin`, `/ws/tv`, `/ws/player`) avec broadcast filtré par type. Rétrocompatible : `/ws` reste alias vers admin.

2. **#41** — Réduction du payload WebSocket vers les buzzers physiques. Les buzzers ne reçoivent plus l'`UPDATE` complet (game state inutile depuis v3.4.0/LED_SET). Whitelist : `LED_SET`, `OTA_UPDATE`, `WIFI_CONFIG`, `HELLO`.

3. **#54** — Protocole ACK optionnel sur messages prioritaires (`LED_SET`, `OTA_UPDATE`, `WIFI_CONFIG`). Champ `MSG_ID` + action `ACK` firmware + badge ⚠ frontend + retry configurable.

## Risques et Mitigations

| Risque | Probabilité | Impact | Mitigation |
|--------|-------------|--------|------------|
| Régression LED buzzer (suppression UPDATE → buzzerHub) | Faible | Élevé | Tests avec buzzers physiques + vérif que LED_SET reste envoyé |
| Performance AckManager (beaucoup de buzzers + haute fréquence) | Faible | Moyen | Map en mémoire + goroutine unique suffit pour < 50 buzzers |
| Route `/ws/player` vs `/ws/player/{sub}` conflit mux | Faible | Faible | Tester avec `http.DefaultServeMux` exact match |
| PlayerDisplay partage GameContext avec admin → conflit endpoints | Moyen | Moyen | Vérifier le routing React dans App.jsx avant implémentation |
| Firmware ACK : latence ws_sendAck bloque LED apply | Faible | Faible | ACK envoyé via goroutine ou queue non-bloquante |

L'option A est recommandée (changement minimal).
