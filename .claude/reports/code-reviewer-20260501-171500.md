## Contexte du Bug

Lors d'un self-update, `performRestart()` dans `updater.go` lance le nouveau processus (`cmd.Start()`), attend 1 seconde, puis appelle `os.Exit(0)`. Le nouveau processus démarre immédiatement et appelle `ListenAndServe()`. Si l'ancien processus tient encore le port 80 (fenêtre de chevauchement < 1 s), `ListenAndServe` échouait silencieusement dans sa goroutine, laissant le serveur sans HTTP et sans message d'erreur visible.

---

## Analyse du Fix

### 1. Correction du bug — Boucle retry

**Avant** :
```go
go func() {
    if err := h.server.ListenAndServe(); err != http.ErrServerClosed {
        LogError(game.LogComponentHTTP, "Server error: %v", err)
    }
}()
```

**Après** :
```go
go func() {
    for {
        err := h.server.ListenAndServe()
        if err == http.ErrServerClosed {
            return
        }
        if isPortInUse(err) {
            LogWarn(game.LogComponentHTTP, "Port %d busy, retrying in 500ms...", h.port)
            time.Sleep(500 * time.Millisecond)
            continue
        }
        LogError(game.LogComponentHTTP, "Server error: %v", err)
        return
    }
}()
```

**Verdict** : La logique est correcte.

- Reuse de `*http.Server` entre tentatives : **valide**. `ListenAndServe` ne modifie l'état interne (`inShutdown`) que si `Close()`/`Shutdown()` est appelé. Un échec de `net.Listen()` (port busy) ne corrompt pas l'état du serveur — la prochaine tentative est saine.
- Pas de busy-wait CPU : `time.Sleep(500ms)` entre chaque tentative. ✓
- Pas de goroutine leak : la goroutine se termine sur `ErrServerClosed` (shutdown normal), sur erreur non-port-busy (erreur inattendue), ou continue de retry si port busy. ✓
- Erreurs inattendues traitées : le `return` final après `LogError` évite une boucle infinie sur d'autres types d'erreur. ✓

### 2. Compatibilité Stop() / ErrServerClosed

`Stop()` appelle `h.server.Close()` qui positionne le flag `inShutdown` du `*http.Server`.

- Si la goroutine est en `time.Sleep(500ms)` : elle se réveille, appelle `ListenAndServe()`, qui vérifie `shuttingDown()` → retourne immédiatement `ErrServerClosed` → goroutine sort proprement. ✓
- Si la goroutine est en `ListenAndServe()` active : `Close()` provoque un retour avec `ErrServerClosed` → goroutine sort. ✓
- Délai maximal de 500ms entre `Stop()` et la sortie de la goroutine en cas de retry en cours — acceptable. ✓

**Aucun effet de bord sur Stop() / ErrServerClosed.** ✓

### 3. Scope minimal

Seul `server-go/internal/server/http.go` est modifié. Le diff est chirurgical : 16 lignes ajoutées dans `Start()` + 1 fonction helper `isPortInUse()`. Aucun autre fichier touché. ✓

## Problemes Mineurs

> Suggestions d'amélioration — non bloquants pour le merge

### [MINEUR] isPortInUse() : strings Windows potentiellement locale-dépendant

- **Fichier** : `server-go/internal/server/http.go:130-133`
- **Description** : `"Only one usage"` est le début du message Windows WSAEADDRINUSE **en locale anglaise**. Sur Windows en langue française (ou autre), le message système sera traduit (ex: *"Une seule utilisation de chaque adresse de socket..."*), et le match échouera. La branche Linux (`"address already in use"`) est insensible à la locale car c'est un message Go/libc hardcodé, non localisé.
- **Impact** : Sur Windows non-anglais, la boucle retry ne s'active pas — comportement identique à l'ancien code (log error + exit goroutine). Pas de régression, mais le fix n'opère pas sur ce cas.
- **Suggestion** : Pour une robustesse maximale, utiliser une vérification basée sur le code d'erreur syscall. Exemple :
  ```go
  import (
      "errors"
      "syscall"
  )
  
  func isPortInUse(err error) bool {
      var errno syscall.Errno
      if errors.As(err, &errno) {
          return errno == syscall.EADDRINUSE // Linux/macOS
          // Windows: syscall.Errno(10048) = WSAEADDRINUSE
      }
      // Fallback string-based (English)
      s := err.Error()
      return strings.Contains(s, "address already in use") ||
          strings.Contains(s, "Only one usage")
  }
  ```
  Note : `syscall.WSAEADDRINUSE` n'est pas défini comme constante nommée en Go standard — il faut utiliser `syscall.Errno(10048)` pour Windows (nécessite une build tag `//go:build windows`). Acceptable en follow-up.

### [MINEUR] Comparaison err == http.ErrServerClosed non idiomatique Go 1.13+

- **Fichier** : `server-go/internal/server/http.go:114`
- **Description** : `err == http.ErrServerClosed` utilise la comparaison directe au lieu de `errors.Is(err, http.ErrServerClosed)`. Fonctionnellement équivalent ici car `ListenAndServe` retourne `ErrServerClosed` directement (pas de wrapping), mais `errors.Is` est la forme recommandée depuis Go 1.13 (projet sur Go 1.24.0).
- **Suggestion** :
  ```go
  if errors.Is(err, http.ErrServerClosed) {
      return
  }
  ```

## Problemes Informatifs

> Observations — aucune action requise

### [INFO] Pas de cap sur le nombre de retries

- **Fichier** : `server-go/internal/server/http.go:112-125`
- **Description** : La boucle retry est infinie (tant que le port est occupé). Si un autre processus monopolise définitivement le port 80, le serveur retente indéfiniment toutes les 500ms. En pratique, `Stop()` met fin proprement à la boucle via `ErrServerClosed`, et dans le scénario self-update le port se libère en < 1 s. Acceptable pour ce cas d'usage, mais pourrait surprendre en environnement de débogage.
- **Suggestion** : Ajouter un compteur ou timeout (ex: 30 tentatives = 15 secondes) et retourner une erreur fatale si dépassé. Non prioritaire.

### [INFO] isPortInUse() non couverte par les tests

- **Fichier** : `server-go/internal/server/http_test.go`
- **Description** : `http_test.go` existe mais ne couvre pas `isPortInUse()` ni le comportement de retry de `Start()`. La fonction est simple et facilement testable par injection d'erreurs.
- **Suggestion** : Ajouter des tests unitaires pour `isPortInUse()` (cas Linux, Windows, erreur non-port) en follow-up.
